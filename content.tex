\section{Executive summary}

This project is a tool that is able to automatically translates UML class diagrams into Java source code. The goal was not to manually implement a specific model, but to create a reusable algorithm that is capable of generating program structure for any model which follows the defined syntax.

First, a modelling language was specified by defining its concrete syntax (visual elements), abstract syntax (conceptual elements), and well-formedness rules. Each element was then given a meaning by mapping it to an equivalent programming construct. For instance, classes and abstract classes were generated from the shapes, inheritance relationships were translated using extends, and associations were implemented as attributes or lists based on cardinality. 

The generator then produced .java files corresponding to each model entity. Overall, the generated code preserved the relationships defined in the diagram and worked for multiple models without needing to change the algorithm.

\section{Model syntax}

The syntax of the models is defined by the concrete syntax, abstract syntax, and well-formedness rules. Below is a table summarizing these aspects for our UML class diagrams.

\begin{table}[h]
    \centering
    \begin{tabular}{|p{4cm}|p{4cm}|p{7cm}|}
    \hline
    \textbf{Concrete syntax} & \textbf{Abstract syntax} & \textbf{Well-formedness rule} \\
    \hline
    
    Rectangle & Thing & Must have a name written in it \\
    \hline
    
    Parallelogram & Abstract thing & Must have a name written in it, italicized \\
    \hline
    
    Arrow with filled triangle & Directed relationship (has-a relationship) & Must be drawn between two Things and can be circular \\
    \hline
    
    Arrow with empty triangle & Specialization (is-a relationship) & Must be drawn between two Things and must not be circular \\
    \hline
    
    Arrow with diamond & Aggregation (whole-part relationship) & Must be drawn between two Things \\
    \hline
    
    Label on an arrow & Name and cardinality of a relationship & Must have only one name and one cardinality per relationship \\
    \hline
    
    Cardinality (1) & Exactly 1-to-1 association & Each instance of one Thing is associated with only one instance of another Thing \\
    \hline
    
    Cardinality (N) & 1-to-N association & Each instance of one Thing may be associated with multiple instances of another Thing \\
    \hline
    
    \end{tabular}
\end{table}

\section{Algorithm to translate models code}

\textbf{Document the algorithm in a pseudocode and explain it briefly. Did you draw on a
previously studied content? If so, which course? If not, did you find the algorithm
somewhere or did you come up with it?}

\textbf{Pseudocode:}

\begin{verbatim}
Input: draw.io XML file 
Output: Generated .java

// holds all classes and abstract classes
// key stores the type of UML thing (class or abstract), and value stores a list of values and ids
Declare things that map:
	Key = UML thing type (“class”, “abstract”)
	Value = list of (value, thingId)

// holds all arrows
// key stores the type of relationship(inheritance, aggregation, association)
// value stores arrow ids
Declare arrows that map:
	Key = relationship type (“inheritance”, “aggregation”, “association”)
Value = list of arrowId

// holds all arrow labels
// key stores id, and value stores a list of values and arrow ids
Declare label that map:
	Key = labelId
	Value = list of (value, arrowId)
// initialize the keys for the things map
things[“abstract”] ← empty ArrayList
things[“class”] ← empty ArrayList

// initialize the keys for the arrows map
arrows[“inheritance”] ← empty ArrayList
arrows[“aggregation”] ← empty ArrayList
arrows[“association”] ← empty ArrayList

// main loop
For each cell in mxCells:
	// ARROWS
	If cell.style contains “edgeStyle=orthogonalEdgeStyle”:
		// aggregation - diamond
		If cell.style contains “startArrow=diamondThin”:
			append cell.id to arrows[“aggregation”]
		// inheritance - open arrow
		Else if cell.style contains “endFill=0”:
			append cell.id to arrows[“inheritance”]
// association (has) - plain line
Else:
			append cell.id to arrows[“association”]

	// ABSTRACT CLASSES (parallelogram)
	Else if cell.style contains “shape=parallelogram”:
append (cell.value, cell.id) to things["abstract"]
// CLASSES (rectangle)
Else if cell.style contains “rounded=0”:
	append (cell.value, cell.id) to things["class"]
	// LABEL
	Else if cell.style contains “edgeLabel”:
		If label[cell.id] does not exist:
			label[cell.id] ← empty ArrayListla
		append (cell.value, cell.parent) to label[cell.id]

//GENERATE CLASS FILES
For each thingType in things: 
	For each (value, thingId) in things[thingType]
		Create a new file named value +“.java”//CREATE JAVA FILE PER THING
		//WRITE CLASS DECLARATION DEPENDING ON CLASS TYPE
		If thingType == “abstract”:
			Write “public abstract class ” + value
		Else:
			Write “public class ” + value
		//WRITE EMPTY CLASS BODY
		Write “{”
		Write “}”

//HANDLE INHERITANCE RELATIONSHIP
For each arrowId in arrows[“inheritance”]
	//IDENTIFY THE SOURCE AND TARGET THINGS OF THE INHERITANCE RELATIONSHIP
	sourceThingId ← arrow.source
	targetThingId ← arrow.target
	Child ←  thing with id sourceThingId
	Parent ← thing with id targetThingId
	Update child class declaration: //UPDATE CHILD CLASS TO EXTEND PARENT
		“extends parent”

//HANDLE ASSOCIATIONS AND AGGREGATIONS
For each arrowType in[“association”, “aggregation”]:
	For each arrowId in arrows[arrowType]:
		//IDENTIFY THE SOURCE AND TARGET THINGS OF RELATIONSHIP
		sourceThingId ← arrow.source
		targetThingId ← arrow.target
source ← thing with id sourceThingId
		target ←  thing with id targetThingId
		//WRITE RELATIONSHIP NAME AND CARDINALITY FROM LABELS 
relationshipName ←  label value for arrowId
cardinality ← cardinality label for arrowId
//GENERATE FIELDS BASED ON CARDINALITY
If cardinality == “1”:
	Add field to source class:
		“Private target relationshipName;”
Else if cardinality == “N”:
	Add field to source class:
		“Private List<target> relationshipName;”

//AGGREGATION IMPLIES OWNERSHIP, SO INCLUDE TARGET IN CONSTRUCTOR
	If arrowType == “aggregation”:
		Add target as a constructor parameter in source class

//WRITE ALL GENERATED JAVA FILES TO THE OUTPUT
Write all generated  .java files to output directory
\end{verbatim}

In order to extract the necessary information from the XML file, we read the entire file and organize all the information into structured data via Maps so it could be used to later write the Java files. There are 3 main maps: things, arrows, and labels. The things Map stores UML objects (rectangles or parallelograms), and keeps them separate as normal classes or abstract respectively. The arrows Map stores relationships between classes by inspecting the style of the object. The labels Map stores the associated labels attached to arrows, such as its cardinality or other descriptive text. Overall, the main loop iterates through every element in the diagram and classifies it as either a class, abstract class, relationship, or relationship label. 

After the information was extracted and organized, a separate class was used to analyze that information by using the Extraction API. First, it creates a .java file for every detected class or abstract class and writes the corresponding declaration (abstract or normal) with an empty body. Then, it processes the inheritance relationships and updates all the required child classes so they can extend their parent class. Next, it handles associations and aggregations by adding attributes to the source class based on multiplicity: a single object for 1 and a List for N. Finally, all the generated classes are written to the output directory, which is possible with FileWriter.

The pseudocode logic was not taken from a textbook or external source, but rather it was developed independently after examining the contents of the XML file and determining patterns that recurred with the same type of objects/relations. In a previous course, 2OP3 (Object-Oriented Programming), we learned to use a FileReader to read data from a file. However, the actual classification and analyzing logic used in this algorithm was our design.

\section{Implement a proof-of-concept solution}

\textbf{Report the inputs and outputs of the examples you used. Again, an example is a model-code pair, stored in the GitHub repo. In every example, the model corresponds to the syntax you developed previously.}

In this example, the input is a UML diagram that represents a hospital management system. The model follows the syntax that we developed earlier. 

A parallelogram labelled Person is an abstract class. Rectangles are regular classes, such as Nurse, Doctor, etc. There are empty triangle arrows from Nurse, Doctor, and Patient to Person. This represents specialization or “is a” relationship. This means that Nurse, Doctor, and Patient inherit from Person. It is not circular, so they satisfy the conditions. There are filled arrows that are labelled with cardinality N from Nurse to Patient and Doctor to Patient, etc. This represents an association relationship, where a nurse or doctor can be associated with multiple patients. The cardinality N means one to many. There is a (1) relationship from Patient to Bill, and Patient to Room. This means that each Patient has exactly one Bill. There is an aggregation relationship between Patient and MedicalRecord, labelled with cardinality of 1. This means that each Patient has exactly one MedicalRecord. 

The output of this model is generated Java classes. The generator creates one Java file per shape in the diagram. Person is an abstract class because it’s a parallelogram, and other classes are regular because they are a rectangle. Each relationship in the UML diagram becomes a field in the Java class that is generated. Cardinality 1 creates a single object, whereas Cardinality N creates a List of that type. For example, Patient.java is generated to extend Person. Patient has a one-to-one relation with Bill, Room, and MedicalRecord; the generated class includes these private fields of type Bill, Room, and MedicalRecord. It also contains a list of Appointments due to cardinality N, as a patient can have many appointments. 

This shows that the generator correctly places the UML diagram logic into code and follows the translational semantics in task 2.

\section{Reflections}

\textbf{Assess the complexity of extending your code generator to generate code in the other language: in Python, if you generated Java code in Tasks 2-3; and Java, if you generated Python code in Tasks 2-3. Would this be a complex task or a fairly straightforward one? How about generating C code? What is the main difference between extending your generator to Java or Python vs to C?}

Extending the code generator in Python instead of Java would be fairly simple. The overall structure of classes, inheritance, and fields is similar. The main change would be adjusting syntax, such as removing type declarations, changing constructors, and adapting list structures. The conceptual model to code would remain mostly the same. 
Generating Java or Python is easier than C. C does not support classes, inheritance, or objects directly so many concepts in this model would need to be simulated using structure, function pointer, and memory management. This makes the translation more complex and less direct. Java and Python are OOP languages, which map naturally to class diagrams, while C is primarily procedural, so the conceptual model does not translate so easily. 

\textbf{How does your code generator compare to an LLM-based model, e.g., ChatGPT
conceptually? What are the differences and similarities? What are the benefits and limitations/challenges of your solution and what are the benefits and
limitations/challenges of using an LLM for generating code? Which one would you use in which situation?}

Our code generator and LLMs can both generate code, but they work in different ways. Our code generator is based on rules and follows them based on our design. For example, rectangles become classes, and an empty triangle arrow is extended. The code generated by our code generator produces the same output every time. It does not guess or add any extra information. LLMs work differently, as they generate code based on what it has learnt from training data. It does not follow the rules till we specify that completely. It can add information we don’t need to the code if the information we gave it was missing or not specified. 
There are some similarities between them. They both can automate turning UML to code by using the rules given, and they both have knowledge about the structure of the code. They can reduce coding manually. The main differences are that the generator follows the structure given, whereas LLMs can hallucinate and are flexible with the code generated. 

The benefits of the code generator are that it follows the rules of the UML diagram and the generated code matches the diagram exactly. This makes it very reliable. However, it can not handle missing information, as if the diagram is not complete, then the generator can only produce code for whatever is given. The benefits of an LLM are that it can give improvements, handle incomplete information, and provide additional logic. However, it might give the wrong answer as it can hallucinate, and the solution might be inconsistent. Sometimes, it may give code that can compile and run, but the code produced is not what was expected. 
Our code generator is a better choice when we need the code generated to be consistent, follow rules, and adhere to academic guidelines. LLMs are a better choice when we want to experiment, explore ideas, and generate new ones.

Two major language workbenches in the Eclipse ecosystem are Sirius Web and Capella. 
Sirius Web is a web-based tool used to create visual modelling languages and domain specific languages (DSLs). It allows developers to design custom diagrams and modelling environments for specific systems. 
Capella is an open-source Model-Based Systems Engineering (MBSE) tool that supports system modelling using the Arcadia method. It provides a structured environment for designing complex systems. 
In Catan, these tools could be used to visually model components like players, tiles, buildings, and relationships before writing that Java code. They could help organize the system design and potentially generate parts of the code. This would make the design clearer, more structured and easier to extend if the game became more complex.
